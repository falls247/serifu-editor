# ADR-0033：SAM3のメモリマップ・直接割当てとアプリ無操作解放

- 日付：2026-10-25
- 状態：メモリマップ＋直接割当て、アプリ無操作解放、設定UIを採用・実装。meta構築とCPUスレッド制限は未採用。
- ADR-0032の既定600秒・推論中心の判定を、既定900秒・アプリ全体の操作による判定で置き換える。
- 対象：[省メモリ化SOW](../../sow/SOW_20261025_sam3_memory_loading.md)
- 実測と検証：[実装報告](../sam3-memory-loading-report.md)

## 背景

現行SAM3はCPU上のモデルを初期化後、checkpoint全体をCPUへ読み込み、重みをコピーしてCUDAへ転送する。モデル・checkpoint・ファイルキャッシュが重なり、WSLメモリとディスク負荷が増える。再起動後に推論失敗は再発せず、推論エラーの原因とロード時のメモリ増加を同一視しない。

## 採用した判断

固定SAM3依存との接続を`backend/app/model_loader.py`へ隔離する。パス文字列で`torch.load(weights_only=True, map_location="cpu", mmap=True)`を実行し、公開builderでCPU構造を作る。`load_state_dict(strict=True, assign=True)`でcheckpointの重みを割り当て、GPUへ転送する。元モデルのdtype、共有parameter／buffer、非永続buffer、upstreamのCUDA位置情報キャッシュを維持する。欠損・余剰・形状の不一致はロードエラーにする。旧シリアライズ形式だけ構築前にmmapなしへ分岐し、任意例外・OOMで二重ロードしない。

CPUのランダム初期化は残る。meta構築の調査では、固定ViTの`torch.linspace(...).item()`で失敗した。さらに明示的CUDA生成と事前計算bufferの置換が必要になるため、内部factoryの複製やPyTorch全体の差替えを追加せず、meta構築は未採用とした。assignはCPU構造でも使えるため、metaから独立して採用した。

モデル解放時はautocastキャッシュも破棄する。固定trackerが継続的なautocastコンテキストを開き、モデル参照を外しても変換済み重みが残ることを実測したため。GPU lockとengine lockの下で実施し、推論精度やCPUスレッド数は変えない。

`.venv`直接編集、PyTorch全体へのmonkey patch、無条件の再ロードは採用しない。量子化・精度変更・CPU常駐待機・WSL設定変更は今回の判断に含めない。

## アプリ全体の無操作による解放

既定しきい値を15分（900秒）とし、SAM3以外の文字編集・画像切替・ポインタ・キー・タッチなども操作として扱う。アプリ共有クライアントから実操作のみを集約通知し、バックエンドの単調時計で最後のアプリ操作・ロード完了・推論終了の最新時刻から計時する。health監視、自動保存、タブを開いたままの状態は保持期限を延長しない。GPU lock内の再確認と実行・待機中の解放抑止は維持する。

UIに1〜240分・整数の入力と「保存」を設ける。保存済み有効値、秒単位の環境変数、既定900秒の優先順で復元する。秒単位の旧設定は丸めず表示する。モデルパスの部分更新互換性と設定ファイルの原子的置換を維持し、保存失敗では実行時設定も変更しない。無操作設定だけではモデル世代・読込み回数を変更しない。

アプリ単位でtrustedなポインタ・キー・入力・クリック・wheel・touchイベントを集約し、最大約5秒ごとに操作があった場合だけPOSTする。自動scrollイベントはユーザー起因と区別できないため数えず、wheel・タッチ・キー・スクロールバーのポインタ操作を数える。APIはHost／Origin・1024バイト上限・値を検証する。通知は入力内容を含まず、セッション、連番、世代、操作経過時間、healthで得た短命なサーバー時刻窓を送る。10秒超の操作経過、旧連番、別世代、30秒以上前の時刻窓は期限更新に使わない。隠れた画面では未送信の直近操作だけ送信を試み、失敗した通知を再送しない。

複数タブの操作を合わせるが、モデル不在時の編集だけではロードしない。API未接続・通知失敗は通常編集を妨げず、再接続だけで古い操作を現在へ置き換えない。設定応答とhealthのリビジョン、サーバー起動世代を照合し、古い応答による設定の巻戻しを防ぐ。

従来の600秒を900秒に置換するだけでは、文字編集を続けていても解放される問題が残るため採用しない。長いしきい値はGPU占有時間を増やす。OSキャッシュの強制削除は再読込みを遅くするため、モデル解放に組み込まない。

## 代替案と影響

- 現行方式の維持：保守は容易だが起動時の重複メモリと初期化コストが残る。
- GPU上で直接モデルを構築：CPU確保は減らせてもGPUピークと構築互換性の問題がある。
- WSL上限の縮小：Windows側の割当てを抑えてもswap・ディスク待ちが増える可能性がある。
- CPUモデル待機：再ロードは速くできるが常駐RAMを増やし、今回の目的と逆行する。

メモリマップでファイルI/OやWSLキャッシュはなくならない。CPU構築が残るため、ロード中のCPUモデル分は必要。今回の各3回では最大RSSとswap書込みの低下、重み・推論結果の一致を確認した。キャッシュ冷条件、Windows側VmmemWSLの縮小量は未確認で、計測値は他環境での削減量を保証しない。
