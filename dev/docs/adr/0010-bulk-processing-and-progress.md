# ADR-0010：一括処理の並列化、容量制限、進捗、新しい高速保存形式

- 状態：採用（性能の受入判定は実装後報告を参照）
- 記録日：2026-10-10（日本時間）
- 対象SOW：[SOW_20261010_bulk_performance.md](../sow/SOW_20261010_bulk_performance.md)
- 調査基準：`b35abd5` とページ分割・サムネイル・輪郭の作業ツリー変更

## 背景

約500枚の読込・保存で、逐次デコード、メインスレッド描画、同期サムネイル変換、全画像のBase64 JSON化が負荷になる。50／100件表示で画面の保持量は抑えられるが、一括処理の実行経路にも改善が必要。各操作の進捗と中断結果を一貫して表示したい。

## 決定

### 1. Workerと上限付きキュー

画像の準備・サムネイル・PNG生成はWorker内で共通描画を使う。初期Worker数2、読込中は最大4、PNGは2とし、稼働画像の概算容量、書込み待ち件数・byte、字形キャッシュを制限する。無制限の全件並列は行わない。フォント読込・描画一致を確認し、API・描画の非対応対象には既存経路を使う。

ファイル書込みはメイン側で制御し、PNG生成と重ねる。操作開始時のスナップショットとページ番号を保存先・順序の基準にする。取消時は操作IDで古い応答を棄却し、画像・Canvas・保留結果を解放する。

### 2. 読込と画面更新

候補番号を固定し、最初の表示範囲の準備を優先する。EXIFのないJPEGは縮小ビットマップでサムネイルを準備し、元画像Blobと元寸法を維持する。準備済みページを分割して採用し、全件完了前に本文・配置編集を許可する。読込中の構造変更や持ち出し保存は制限して順序を守る。サムネイルは長辺320pxのBlobとし、URLを明示的に破棄する。

一括レイヤー操作は準備と適用を分け、1操作の履歴を維持して画面更新をまとめる。一時保存は既存画像IDを一括取得し、新規画像だけを準備する。保存の原子性とrevisionの意味を維持する。

### 3. キャッシュ

PNGには128MiB上限のメモリ内LRUを導入する。キーに原画像ID、寸法、描画版、フォント状態、描画に影響する全レイヤー入力を含める。ページ番号・選択・表示設定はキーから除外する。変更がなければPNGを再利用し、新しい保存先への書込みは毎回行う。

### 4. 進捗

共通操作モデルで段階、確定件数、成功・失敗、対象名、経過時間、中断を管理する。複数段階の割合は段階内の値として表示し、操作全体の割合と混同させない。総数未確定は不定進捗。ファイルclose、DBトランザクションcomplete、ダウンロード開始の違いを保存状態に反映する。

前景の一括操作と自動保存の表示を分け、自動保存は前景処理・読込終了後に延期する。UI更新は100ms間隔に集約し、終了・失敗・段階変更は即時更新する。

### 5. 編集データの高速形式

画像をBase64へ変換せず、原画像BlobをUTF-8 manifestとともに単一 `.serifu` ファイルへ収録する。コンテナ版は1、内部の編集モデル版は6。magic、manifest長、manifest、asset順の画像バイト列を連結する。圧縮依存ライブラリは追加しない。

従来JSONのversion 1〜6は読込・出力を維持する。利用者が高速形式／従来JSONを選べるようにし、高速形式を初期選択にする。一括PNGに添える編集データも選択形式に従う。従来JSONは逐次出力・Worker解析で大きな同期処理を避ける。

フォルダハンドル、サムネイル、DOM、Undo履歴は高速形式にも永続化しない。破損・中断時は既存の一覧を保つ。

## 代替案と比較

- 全件の `Promise.all` は待ち時間を減らせてもメモリとI/Oの競合を増やす。上限付きキューを採る。
- メインスレッドの分割処理だけでは1枚の重い描画を分離できない。Workerを基本とし、分割処理を代替経路にも用いる。
- PNGを無制限に記憶すると数百枚で容量が膨らむ。byte単位のLRUを採る。
- JSONだけを継続するとBase64の容量増加が残る。高速形式を追加し、旧形式との移行経路を維持する。
- ZIPは一般ツールで展開できる利点があるが、圧縮・ライブラリ・配信管理を増やす。今回は原画像を保持する単純な版付きコンテナを採用する。
- 見かけの全体パーセントを段階の固定重みで作る方式は画像や書込み先により実時間とずれる。段階番号と段階内件数を表示する。

## 結果・懸念

Workerとプレビューで端末フォールバックや字形が異なる可能性、並列化によるメモリ増加、高速形式が旧アプリでは読めないことが主要な懸念。描画比較、容量制限、従来JSON出力で対処する。

ディスク速度・実画像・ブラウザにより改善幅は変わる。性能値は実装前には未確認。基準と変更後を同条件で比較し、SOWの目標未達を成功と報告しない。

SOWで提案したADR-0009は、先に採用された名前付きプリセットのADR-0009と番号が重複したため、採用時にADR-0010へ変更した。画像Worker初期2個・読込最大4個、稼働概算256MiB、保留2件・64MiB、PNG LRU128MiB、コンテナ版1を採用。PNGの保留容量は元画素数の非圧縮見積もりで投入を抑制し、実際の保留Blob容量も計測する。未知の寸法は単独処理する。

画像追加と編集データ読込の画像準備は20件ずつメタ情報を取得し、寸法に応じて最大4ジョブを動かす。読込完了後は2 Workerへ戻す。画像追加は採用済みページを編集可能にし、編集データ読込・一時保存復元は検証と準備が全件完了するまで一覧を変更しない。画像は元Blobと寸法を保持し、表示中だけHTMLImageをデコードする。

JSON変換Workerは単独で再利用し、ページごとの逐次出力にする。高速形式は原画像をそのまま連結し、メタ情報は16MiBを上限とする。DB版は1を維持する。既存画像IDを一括取得し、追加Blobだけを準備して単一トランザクションでメタ情報と画像を確定する。コミット前の取消と、保存中の後続編集を検証した。

検証と生成画像の測定値は[実装後報告](../bulk-performance-report.md)を参照。実画像・実ディスクの速度は未確認。

## 追加判断：保存先選択APIのない環境

Brave環境で直接フォルダ保存を開始できず、完了した進捗が「準備」のまま残るという報告を受け、APIがない場合はPNGと選択形式の編集データをZIPとしてダウンロードする。API対応環境の直接保存は維持する。UTF-8の非圧縮ZIPをBlobの参照で組み立て、CRC32を分割計算する。ZIP64は導入せず全体4GiB未満・65535ファイルまでに制限する。収録Blobを全件保持する容量増加と、ダウンロード開始後の保存確認ができない点を制約とする。通常ダウンロードでは未保存状態を解除しない。

進捗欄は暗色テーマへ統一し、操作終了で閉じ、結果をfooterへ残す。保存先選択とフォルダ準備の待機も中断でき、古い応答は次の保存へ混入させない。
