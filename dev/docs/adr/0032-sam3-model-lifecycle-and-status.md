# ADR-0032：SAM3モデルの寿命と状態監視を画像要求から分離する

- 状態：提案。未採用・未実装。
- 記録日：2026-10-18
- 調査時HEAD：`88b6e110746a1c9acc59a258c6beb99c05d264b5`
- 対応計画：[SAM3再読み込みのSOW](../SOW_20261018_sam3_reload_lifecycle.md)
- 関連：[ADR-0023](0023-sam3-mask-effects-and-storage.md)。GPU処理の直列化、要求取消による古い結果の無効化は維持する。

## 背景

現行のモデルは起動時にロードし、アイドル時に完全解放する。解放後の再ロードは画像ジョブの中で行う。ロード中の画像切り替えはジョブを取り消すが、実行中のロードは継続する。ロード後にジョブが終了すると、以前のアイドル時刻が残り、次の監視周期で再解放する条件がある。SOWの同期モックでこの状態遷移を確認した。実GPUでの再現・所要時間は未確認。

画面のモデル状態は各パネルが取得したhealthに依存する。画像ジョブのpollは取消で終わるため、別画像からロードの進行・完了を継続して確認する仕組みがない。

## 提案する判断

1. モデルのロード・寿命・世代はバックエンドのモデル管理が所有する。起動と再ロードの共通処理は進行中のロード1件を共有し、画像要求の取消から切り離す。既存のGPU lockと実処理の終了待ちを維持する。
2. ロード成功時刻とGPU処理終了時刻を分け、新しい方をアイドル判定の起点とする。ロードを待っていた画像が取り消されても準備完了時刻は更新する。health取得は利用時間に数えない。
3. ブラウザ側は全画像で共有するクライアントにモデル状態と監視を置く。パネルは購読し、画像要求の状態と別に表示する。パネル数に応じて監視通信を増やさない。
4. 画像切り替え時に旧要求・候補を無効化する仕様を維持する。別画像の明示的な検出要求は共有ロードの完了を待ち、自分の入力で推論する。画像選択だけでは自動推論しない。
5. まず既定600秒の完全解放を維持する。CPUモデル待機は、段階別計測とメモリ上限・完全解放への退避を備えた任意設定の比較案とし、速度・メモリの条件を満たすまで既定化しない。

## 比較した案

| 案 | 判断理由 |
|---|---|
| 画像切り替え中は操作を禁止する | 待ち時間を画像閲覧・編集に使えなくなるため見送る |
| 切り替えのたびにモデルロードを中止・再開始する | 実スレッドの即時停止が難しく、再構築コストも増えるため見送る |
| パネルごとにhealthをpollする | 多数画像の表示で通信が増えるため、共有監視を提案 |
| GPU保持時間だけを延長する | 頻度は減るが、古い時刻・表示の問題と完全解放後の構築コストを解決しない |
| 常にGPU上に保持する | 他のGPU処理へメモリを返せないため、既定にはしない |
| CPU待機を直ちに既定化する | RAM・swap・退避時ピーク・予測器のdevice整合が未確認のため、比較評価を先行 |

## 想定される結果・制約

取消後の不要な再解放を防ぎ、モデル読み込みの状態を画像移動後も追跡できる。一方、完全解放後のbuilder再実行は残るため、表示と時刻の修正だけでロードそのものの短縮は保証しない。

共有ロードの取消伝播、モデルパス変更時の世代更新、遅延health応答、終了処理の待機には回帰検証が必要。CPU待機を採用する場合はRAM占有が増える。GPU上の隠れた参照、CPU復帰後のテキスト・ポイント・候補修正の同等性を実機で確認する。

## 採用時に更新するもの

SOWの受入条件、`backend/app/jobs.py`・`engine.py`・health契約、`src/sam3-client.js`・`sam3-ui.js`、関連テスト、`docs/index.html`を同じ実装変更内で更新する。採用が決まった段階で本ADRの状態と、CPU待機を含む採用範囲を確定する。
