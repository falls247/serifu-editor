## 1. 目的・成果物・対象外

再読み込みの不要な繰り返しを防ぎ、別画像へ移動してもモデル全体の読み込み状態を追跡できるようにする。残る再読み込み時間を段階別に計測し、完全解放と復帰速度のトレードオフを判断する。

今回の成果物は本SOWと提案状態のADR、開発文書の索引更新。実装、実GPUでの性能測定、環境変数・モデルパスの変更、モデルの実ロード、コミットは含めない。

将来の実装でも、画像を選ぶだけで他画像のプロンプト・ポイントを引き継いだ自動推論は行わない。保存形式、確定済みマスクの編集、公開版のSAM3利用条件は変更対象外。

## 3. 問題の切り分け

### 3.1 完全解放後に再構築コストが発生する

現行の解放はGPUからCPUへの退避ではなく、モデルオブジェクトの破棄。次回はモデル構築・重み読込・GPU転送をやり直す。ロード後の画像前処理、画像エンコード、推論、画像期限切れによる再送信も体感待ち時間に含まれ得る。

したがって、監視表示の改善だけではモデル構築そのものは速くならない。GPU保持時間の延長も再ロードの発生頻度を減らすだけで、完全解放後のロード処理の高速化とは区別する。

### 3.2 取消後にロード済みモデルをすぐ再解放し得る

現行処理では次の順序が成立する。

1. 最終利用から600秒を過ぎ、モデルが解放される。最終時刻は以前のまま残る。
2. 画像Aの検出でモデルを再ロードする。
3. ロード中に画像Bを選び、Aのジョブが`cancelled`になる。
4. ロード自体は完了するが、Aは推論前に終了する。最終時刻が更新されない。
5. 実行・待機ジョブがなくなると、次のmaintenanceで期限超過と判定され再解放する。
6. Bで検出を要求すると、再びモデルを構築する。

**モックで再現済み。** 既存の`JobManager._run()`・`_maintain()`を使い、最終時刻を601秒前、モデルを未ロードに設定。ロード完了境界でAを取り消し、10msの監視周期で再解放され、Bで再ロードする流れを確認した。呼出し順は`load → unload → load → infer`、Bの最終状態は`ready`。アプリ・テストファイルは変更していない。

この確認ではGPUを使用せず、`asyncio.to_thread`を同じ関数を同期実行するモックに置換した。実行環境内で別途試したスレッド版は、スレッド終了通知後のasyncio待機から復帰せず中断したため、並行実行の実証には用いない。モック結果は状態遷移と時刻更新漏れの根拠であり、実GPUの所要時間や実ブラウザでの発生頻度を示さない。

### 3.3 画像の要求状態とモデル全体の状態が別々に動く

同じ表示範囲ですでにマウント済みのBには、新規health取得がない。以前の「準備完了」「未ロード」表示が残り得る。未マウントのBなら初期healthを取得するが、その後の状態変化を定期的には追跡しない。Aのジョブpollも取消で止まるため、モデルはロード中でもBの要求欄は「待機中」になる。

「止まったように見える」には少なくとも次の条件があり、実装時に別々に再現する。

| 切り替え時点 | 現行のバックエンド | 必要な表示・扱い |
|---|---|---|
| 起動時のロード中 | ページ切り替えから独立して継続 | Bにもモデル読込中を表示し、完了を追跡する |
| Aの推論要求から始まった再ロード中 | 開始済みロードは継続。取消後の再解放は§3.2の対象 | モデル読込中とAの要求取消を分ける |
| アップロード中など、まだ推論要求が未受理 | Aの取消により再ロードが始まらない場合がある | 未ロードと表示。Bの検出等の明示要求で開始する |
| ロード後・推論中 | Aの結果は破棄するが、実行処理の即時停止は保証しない | Bの推論待ちとモデル準備完了を分ける |

画像選択だけで新しいロード・推論が必ず始まる仕様にはしない。別画像へ切り替えても、開始済みロードの監視を継続し、Bで検出を要求した場合はそのロードを再利用する。

## 4. 修正方針・提案差分（未実装）

### P0：アイドル時刻とロードの所有者を整理する

- `last_model_ready_at`等を導入し、初回・再ロード・将来のCPU復帰の成功時に必ず記録する。アイドル判定の起点は同じモデル世代の準備完了とGPU処理終了のうち新しい時刻とする。取消済みジョブでもロード成功の記録を省略しない。
- `last_inference_finished`を安易にロード完了時刻へ流用せず、推論時間の計測とモデルの保持期間を分ける。パス変更では旧モデルの時刻・エラー・キャッシュ世代を無効にする。
- ロードはバックエンドのモデル管理が所有する。共通の`ensure_model_ready()`に起動ロードと再ロードを集約し、進行中の1件を共有する。画像ジョブの取消で共有ロードを取り消さず、ジョブ自身の結果だけを無効化する。
- 現行でもGPU lockによりロードは直列化されている。画像切り替えのたびに並列ロードしているとは判断しない。共通化の目的は、所有者・状態・時刻更新を一致させる点にある。
- ロード・推論・解放・モデルパス変更のGPU排他を維持する。共有タスクの待機取消を分離しても、実スレッドの終了前にlockを解放しない。終了処理では実行中ロードの完了を待つ。
- 初期段階は既定600秒の完全解放を維持する。health監視・サムネイル選択をモデル利用と数えず、監視だけでGPU保持時間を延ばさない。

### P0：モデル全体の状態を共有して監視する

- 全画像で共有する`Sam3Client`に、モデル状態のストア・購読・監視を追加する。画像ごとの`draft.status`はアップロード／推論／候補確認に限定する。
- 既存healthにモデル世代、ロード開始・準備完了時刻、取得可能な処理段階等を追加する案とする。旧応答で追加項目がなくても既存statusで動く。healthはGPU lockやロード完了を待たずに返す。
- 監視タイマーと通信中のhealth要求はクライアント全体で各1件。パネルを50件マウントしても50本のpollを発生させない。画像切り替え・再マウント時は共有値を即表示し、古い値なら再取得する。
- 初期案のpoll間隔はロード中1秒、通常10秒。通信失敗時は段階的に間隔を延ばす。非表示タブでは監視を抑制し、再表示時に再取得する。設定保存・取得の世代を照合し、遅れて届いた旧応答で表示を戻さない。
- モデル状態が変わったときだけ表示を更新する。毎秒パネル全体を再構築せず、フォーカス・編集中のプロンプト・未保存モデルパスを保持する。
- 表示例は「モデル：読込中（経過35秒）」と「この画像：待機中」。Bが検出を要求した場合は「この画像：モデルの準備待ち」とし、準備完了後にBの入力で推論する。古い画像の候補は反映しない。
- ロード失敗・接続断・未ロードを区別する。実測可能な段階と経過時間を示し、根拠のない完了率や残り秒数を表示しない。現段階では独立した事前ロードAPIを必須としない。

### P1：ロードの時間を分離して計測する

同じcheckpoint・画像・入力で、以下を単調増加時計で記録する。CUDA処理の段階計測では、必要箇所の同期を含めた診断計測と通常運用の時間を分ける。

| 計測対象 | 内容 |
|---|---|
| 起動／再ロード | 起動理由、モデル世代、要求受付、GPU lock待ち、依存import、builder、processor生成、準備完了 |
| builderの内訳 | CPUモデル構築、checkpoint読込・state適用、GPU転送。固定依存に診断用フック等が必要なら影響を分離して記録 |
| 推論 | 元画像取得・転送、期限切れ再転送、前処理・画像エンコード、推論、候補変換、ブラウザ受信まで |
| メモリ | プロセスRSS（常駐メモリ量）、利用可能RAM、swap、PyTorchのGPU allocated／reserved。GPU全体の占有とは分ける |

プロンプト本文や画像内容は性能ログに含めない。初回起動、OSキャッシュが温まった完全再ロード、長時間放置後の再ロード、取消後の次画像を分ける。OSキャッシュを意図的に消去する操作は今回も将来の通常検証にも含めない。

### P2：CPU待機による復帰短縮を比較評価する

ロード計測後、**GPUからの解放時にCPU側のモデルを保持する方式を任意設定で試す**。完全解放の既定動作を直ちに置き換えない。

| 案 | 効果 | デメリット・採否 |
|---|---|---|
| GPU保持時間を延長 | 再ロードの回数を減らす | VRAM占有が長引く。既存の`SAM3_MODEL_IDLE_SECONDS`で調整可能だが、完全解放後の速度は改善しない |
| GPU解放→CPU待機→時間・容量制限で完全解放 | CPU待機中はcheckpoint再読込とモデル再構築を省き、GPUへの復帰を試せる | RAM増加、退避・復帰時間、swapによる逆効果。P2の比較対象 |
| 重みだけCPUにキャッシュ | ディスク読込を省く | モデル構築・重み適用は残り、RAMも増える。完全なCPUモデル待機との比較で判断 |
| `mmap`・`meta`等を使ったbuilder変更 | 読込・初期化を省ける可能性 | 固定依存との適合、重み適用、ポイント推論の互換性確認が必要。計測前の一括導入は見送る |

CPU待機案の条件は次のとおり。

- GPU上の特徴量・予測器のキャッシュを破棄し、モデル・processor・予測器が保持するテンソルとdevice参照を確認する。単に`model.to('cpu')`を足して完了としない。CPU推論は追加しない。
- CPU待機中の容量上限・保持期限・利用可能メモリの下限を定義する。`.pt`のファイルサイズを実際のRAM必要量と同一視しない。退避時の一時的なピークも計測する。
- メモリ不足やGPU復帰の失敗でCPUキャッシュが使えない場合は参照を破棄し、完全ロードへ最大1回フォールバックする。無限の再試行や複数モデルの同時保持を避ける。
- モデルパス・重みファイルの識別情報・モデル世代が変わったら再利用しない。退避・復帰・完全解放も共通の排他制御に含める。
- 設定名・既定値は計測後に確定する。将来の設定候補は現時点で利用できる環境変数として説明しない。

## 6. 実装時の検証・受入条件

### 必須の機能・回帰検証

1. 初回ロード中にA→B→Cと選択しても、サーバーのロードは1回で完了する。既存マウント・未マウント・表示範囲をまたぐ切り替えを確認する。
2. 完全解放→Aで再ロード→ロード中にAを取消→ロード完了の順序で、待機ジョブがなくても準備完了から保持期限を計り直す。直後の監視周期で解放せず、Bの検出が再構築なしで動く。
3. ロード完了直前・直後の取消、最後の待機ジョブの取消、パス変更後の取消でも同条件を満たす。古い候補・エラーを新画像へ反映しない。
4. Bからロード中に新しい検出を受け付け、完了した共有モデルでBを推論する。GPU処理が並列化されず、実行中の古い推論は結果だけを無効化する。
5. 表示中のアクティブ画像では、モデル状態変化を原則1秒のpoll＋通信時間以内に反映する。画像要求の「待機中」をモデル未ロードの意味で使わない。通信失敗時は接続状態を表示する。
6. マウントが50件でもhealthの監視元は1個、同時health要求は最大1件。全パネル破棄・タブ再表示・再マウント・モデルパス保存・遅れて到着したhealthを確認し、タイマーと購読を残さない。
7. モデル不在、ロード失敗、GPUメモリ不足、API停止・再接続で入力を保持して明示再試行できる。推論180秒とクライアント待機10分は別の範囲なので、ロード待機と推論待機の終了条件を説明する。秒数を延ばすだけの対策にしない。
8. 通常表示・元画像FOCUS・ライブプレビューFOCUS・原寸表示、マウス・タッチ・キーボードで該当する操作と表示を確認する。Enter検出、ポイント追加、既存の取消・保存を維持する。
9. 実装時は操作説明書のモデル状態、画像切り替え時の取消、再ロード待ち、エラー時の対処を更新する。P2を採用した場合は解放方法とメモリ上の制限も説明する。

### 実GPUの性能評価

- 既存環境のRTX 4070 Ti SUPER、同じ重み・入力、同時稼働アプリを記録して比較する。起動・完全再ロード・CPU復帰を混ぜず、各条件5回以上の中央値と最大、メモリのピーク・解放後を報告する。
