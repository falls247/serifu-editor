# SAM3初回ロードと推論失敗の調査

調査日：2026-10-25。ブランチ：`fix/sam3-error-diagnostics`。

## 確認済みの事実

- 起動中APIのhealth：初回ロード418.484秒、依存14.222秒、builder 404.255秒、processor 0.005秒。取得時はready、ロード回数1。
- モデルはext4上の`/home/falls247/dev/models/vision/sam3.pt`、3,450,062,241バイト。`load_from_HF=False`で、ダウンロード待ちではない。
- 固定SAM3依存はCPU上でモデルを構築後、`torch.load(map_location="cpu")`、`load_state_dict()`、GPU転送を行う。CPUモデルと読込み中の重みが同時に存在する。
- バックエンドの180秒制限はロード後の推論に適用される。3分超のロード自体が、報告の汎用推論エラーを直接発生させる実装ではない。
- 利用者はポイント検出が毎回失敗し、`SAM3 inference failed (RuntimeError)`が記録されると報告。提示されたジョブIDからも`INFERENCE_FAILED`を確認した。状態取得のHTTP 200は推論成功を意味しない。

起動中サーバーを維持したまま、診断用モデルを追加ロードした測定。測定順、OSのファイルキャッシュ、メモリ圧迫が異なるため、総時間差をスレッド数だけの効果と判断しない。CPU初期化のスレッド数制限は改善候補だが、アプリ既定値は変更していない。

診断中、WSL内の総RAM約15GiBに対し空き約175MiB、利用可能約3.1GiB、swap書込みを観測。利用者からもVmmemWSL約15GB・HDD使用率100%の報告あり。追加ロードは負荷を増やしたため、その後の追加モデル計測を中止。終了時には診断プロセスは既に完了しており、利用可能RAM約10GiB、swap使用約3.2GiBとなった。これらを元の起動時のメモリ状態として扱わない。

重み読込みのI/OとCPU初期化が遅延要因であることは確認済み。元の418秒に占めるディスクI/O・CPU初期化・ホスト側ページングの割合は未確認。VmmemWSLの表示だけから全量をSAM3の常駐RAMやメモリリークとは断定できない。

## 推論の再現結果

同一の256×256合成顔画像を起動中APIへ送信。

| 試行 | テキスト検出 | ポイント検出 |
|---|---|---|
| 1 | 0.506秒でINFERENCE_FAILED | 2.514秒でready・2候補 |
| 2 | 3.524秒でready・1候補 | 0.507秒でINFERENCE_FAILED |

独立したスレッド1の診断プロセスでは、同一顔画像のテキスト・ポイント両方が成功（1候補・2候補）。独立プロセスの別の正方形画像でもテキスト呼出しは例外なしだったが、候補数は記録していない。

画像サイズだけでは失敗を説明できない。実行状態・スレッド依存は仮説であり、確定原因ではない。現行コードが例外本文とトレースバックを破棄するため、実際のRuntimeErrorをまだ特定できていない。GPU OOMとして識別された例外は別コードになるが、メモリ関連の全例外を除外できるわけではない。
