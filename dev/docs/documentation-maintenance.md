# 利用者向けドキュメントの更新ルール

制定日：2026-10-18。

適用入口はルートの [AGENTS.md](../../AGENTS.md)。Agentはアプリ改修前にこの文書を読み、説明書更新または影響なしの記録と検証を終えてから作業完了を報告する。

## 文書の役割

- ルートの[README](../../README.md)：アプリ概要、公開版・操作説明書への入口、通常起動とSAM3の起動に必要な情報に絞る。
- ルートの[操作説明書](../../docs/index.html)：利用者向けの操作手順、保存・復元、ショートカット、対応範囲、トラブル対処をHTMLで説明する。表示スタイルは[manual.css](../../docs/manual.css)。テーマ切替と目次の補助処理はHTML内のインラインスクリプト。
- `dev/docs/`：設計、実装、検証、開発運用の記録。内部の保存形式の版番号やテストコマンドは、利用者の操作に必要な場合を除きこちらへ記載する。

## アプリ改修時の必須対応

**この説明書の作成以降、アプリを改修した際は操作説明書への影響を確認し、利用者向けの動作に影響があれば同じ変更内で`docs/index.html`を更新する。説明書の更新を完了条件に含める。**

対象には次を含む。

- 機能の追加・変更・削除、ボタン名や入力項目、画面構成、操作手順。
- 初期値、制限値、選択・ドラッグ・ショートカットの動作。
- 読み込み、保存、出力、互換性、復元、保存場所の扱い。
- 対応ブラウザ・端末、SAM3の利用条件、エラー時の対処。

内部実装だけの変更で説明書の記載が変わらない場合は、`dev/docs/documentation-impact.md`（初回は作成）に日付・変更対象と `- 操作説明書への影響なし：具体的な理由` を追記し、変更報告やPRにも判断理由を残す。以前の記録の再利用や、チェックを通すだけの説明書変更は認めない。起動要件や手順が変わる場合はREADMEも更新する。詳細な操作説明をREADMEへ戻さない。

## 更新の進め方

1. 実装・画面ラベル・既定値を確認し、説明書の該当節を更新する。通常表示・FOCUS・原寸表示、マウス・タッチ・キーボードなど、該当するモードごとに操作手順と対象外の条件を照合する。同名の機能が複数ある場合は、元画像／ライブプレビューなどの対象を明記する。古い仕様を追記で残さず、現在の説明へ書き換える。
2. 機能の追加・削除で節構成が変わったら、目次と本文内リンクも合わせる。説明書を更新した際は冒頭の対象日も更新する。
3. `docs/index.html`は外部通信やJavaScriptなしでも読める状態を保つ。CSSは相対パスで読み込み、ファイルを直接開く場合・localhost・公開サイトのサブパスで確認する。
4. PC幅・スマートフォン幅で表示を確認する。見出し、リンク、表、キーボードフォーカス、ダーク／ライト両方の表示、テーマの記憶、印刷表示の読みやすさも確認する。
5. `npm run check`と`npm run build`を実行する。配信・ビルドを変更した場合は、ローカルの`/docs/`と`/docs/index.html`が開き、`_site/docs/`へHTML・CSSが出力されることを確認する。アプリの変更には別途、その変更に必要なテストを実行する。
6. 変更報告やPRに、更新した操作説明書の項目と確認結果を記載する。コミットはユーザーの許可後に行う。

新しい画像・CSSなどを追加する際は、`server.mjs`の配信許可リストと`scripts/build.mjs`の公開用コピー対象にも追加する。説明書から開発用の非公開資料に依存しない。

## 更新漏れの自動チェック

`npm run check` は構文確認に加えて `scripts/check-documentation.mjs` を実行する。`src/*.js`、`backend/app/*.py`、`index.html`、`style.css`、`server.mjs`、`assets/`、起動・ビルド・書体取得スクリプトの変更について、同じ差分内の `docs/index.html` 更新、または新しく追加された影響なしの理由を必須にする。テストや開発文書だけの変更は対象外。

- ローカルの既定比較元はHEAD。ステージ済み・未ステージ・未追跡のファイルを含む。コミット後は `npm run check:documentation -- --base <変更前のコミット>` で確認する。
- CIと公開ワークフローはGit履歴を取得し、PRのベースコミットまたはpush前のコミットと比較する。新規ブランチへの初回pushは `origin/main` との共通祖先、公開ワークフローの手動実行は `HEAD^` と比較する。
- Git履歴を取得できない場合はエラーにする。CIでチェックを省略しない。
- 説明書の削除は更新として扱わない。以前からある影響なしの理由は、新しい変更の根拠に使えない。
- 自動チェックが保証するのは、対象ファイルの更新または判断理由が同じ差分にあることまで。説明内容の正確さ・全モードの網羅性は、実装との照合と表示確認で検証する。

2026-10-18のSAM3 FOCUS記載漏れの原因・修正・検証は [調査報告](manual-maintenance-audit.md) を参照。

## 説明書の表示仕様

- 初回はOSの設定にかかわらずダーク表示。上部でダーク／ライトを選べる。
- 選択は説明書専用の`localStorage`キー`serifu-manual-theme`へ記憶する。保存済みの値が不正・未設定ならダーク。保存領域が使えない場合も切替はそのページ内で動作し、本文の閲覧を妨げない。
- 本文はJavaScript無効でも閲覧可能。テーマ切替と目次の現在位置表示は補助機能として扱う。外部スクリプトやネット接続を必須にしない。
- 印刷は選択テーマに関係なく白背景・黒文字。ナビゲーションと表示切替を隠し、折りたたまれた補足も印刷する。
- 大きな宣伝用見出しを置かず、表題・対象環境・番号付きの章・操作手順・項目表を中心とする。PCは固定位置の目次、スマートフォンは折りたたみ式の目次とする。
- 利用者向けの本文・表内の説明・注意書きは「です・ます」調に統一する。操作案内には「選択してください」などの丁寧な表現を使い、体言止めを避ける。見出し・項目名・画面上のボタン名は、内容や実際の表示に沿った表記とする。
- 編集画面の「画像を追加」と「一括保存」の間に、ほかのボタンと区別できる青系の「マニュアル」リンクを配置する。編集画面を維持するため、新しいタブで説明書を開く。

## 開発・公開手順の参照先

コード構成と検証の詳細は[引継書](HANDOFF.md)、設計判断は[ADR一覧](adr/README.md)を参照する。

```bash
npm run check
npm test
npm run build
```

`npm run build`はアプリ・操作説明書・準備済みの書体とライセンスを`_site/`へ出力する。静的配信先にNode.jsは不要。書体を含める場合は先に`npm run fonts`を実行する。

GitHub PagesはSettings → Pages → SourceをGitHub Actionsに設定する。既存の公開ワークフローはmainへのpushまたは手動実行で検証・ビルド・公開を行う。main／masterへの直接pushは禁止。マージや公開は、その時点のユーザーの指示に従う。
